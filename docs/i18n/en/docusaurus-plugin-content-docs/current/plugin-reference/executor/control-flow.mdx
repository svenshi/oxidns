`sequence` and `fallback` define branching, sub-chain calls, and primary/fallback execution.

## `sequence`

<PluginAvailability from="minimal" />

### Purpose

Orchestrates matchers and executors into a pipeline. This is the most common entry executor.

### Example Configuration

```yaml
- tag: seq_main
  type: sequence
  args:
    # Try cache first
    - exec: "$cache_main"
    # Stop immediately on cache hit
    - matches: "has_resp"
      exec: "accept"
    # Arrays of matches are AND-ed together
    # Examples prefer quick-setup matcher expressions directly
    - matches:
        - "client_ip $lan_ip_set"
        - "qname $local_domains"
      exec: "$hosts_main"
    # Rules may also execute unconditionally
    - exec: "$metrics_main"
    # Only forward when no response exists yet
    - matches: "!has_resp"
      exec: "$forward_main"
    # Normalize TTL after a response is available
    - matches: "has_resp"
      exec: "$ttl_main"
```

### Configuration Details

#### `args`

- Type: `array`; Required: yes; Default: none
- Purpose: Defines the rule chain.
- Runtime impact:
  - Rules execute in order.
  - Initialization fails when the array is empty.

#### `args[].matches`

- Type: `string` or `array`
- Required: no
- Purpose: Match condition for the current rule.
- Runtime impact:
  - Multiple conditions are combined with logical AND.
  - Omitted means the rule has no precondition.

#### `args[].exec`

- Type: `string`; Required: no; Default: none
- Purpose: Action to run when the rule matches.
- Supports:
  - plugin references
  - quick setup expressions
  - built-in control flow

### Behavior

- Rules run sequentially.
- A rule with multiple `matches` requires all of them to be true.
- Other `sequence` instances can be called with `jump` or `goto`.

### Built-In Control Flow

Besides plugin calls, `sequence.args[].exec` can also use built-in control flow:

#### `accept`

- Ends the current `sequence` immediately.
- This is an explicit early stop, so outer callers do not continue with later rules.
- Does not build a response by itself; it is usually used after an earlier stage has already produced one.

#### `return`

- Ends the current `sequence` immediately and gives control back to the caller.
- Does not build a response.
- If the current `sequence` was entered by `jump`, the caller continues with the next rule.

#### `reject [rcode]`

- Builds a response immediately and ends the current `sequence`.
- The default `rcode` is `REFUSED`.
- Decimal numeric rcodes and case-insensitive English RCODE names are accepted, for example `reject 2`, `reject SERVFAIL`, `reject servfail`, or `reject NXDOMAIN`; common mappings and meanings are listed in the [DNS Code Reference](../../dns-codes.md#rcode-response-codes).
- Only base DNS RCODEs `0..15` are supported; extended RCODEs require an EDNS OPT and are not generated by this built-in action.
- `reject 0` returns a plain `NOERROR` response and does not add an SOA automatically.
- Stops later rules from running.

#### `mark ...`

- Inserts one or more integer marks, then continues to the next rule in the current `sequence`.
- Supports `mark 1`, `mark 1 2 3`, and `mark 1,2,3`.

#### `jump seq_tag`

- Calls another `sequence`; conceptually this is a subroutine call.
- The parameter must be the target `sequence` tag without `$`.
- If the target `sequence` reaches its tail or executes `return`, the current `sequence` resumes with the next rule.
- If the target `sequence` executes `accept`, `reject`, or another `Stop`, the current `sequence` stops too.

#### `goto seq_tag`

- Transfers control one-way to another `sequence`.
- The parameter must be the target `sequence` tag without `$`.
- Once `goto` runs, the current `sequence` never resumes at later rules.
- If the target `sequence` executes `return`, that `return` is propagated outward.

### Typical Uses

- One readable top-level entry.
- Split cache, local answers, forwarding, and integrations into understandable policy layers.
- Build complex branches with marks and matchers.

<Admonition type="note" title="Notes">

- Referenced plugins must already exist.
- A `sequence` needs at least one rule.

</Admonition>

## `fallback`

<PluginAvailability from="minimal" />

### Purpose

Runs a primary executor first and falls back to a secondary executor when the primary is too slow or fails.

### Example Configuration

```yaml
- tag: fallback_main
  type: fallback
  args:
    # Preferred path
    primary: "forward_fast"
    # Backup path
    secondary: "forward_stable"
    # Let the backup take over after 200 ms
    threshold: 200
    # Keep the backup running in parallel for lower tail latency
    always_standby: true
```

### Configuration Details

#### `primary`

- Type: `string`; Required: yes
- Purpose: Primary executor tag.

#### `secondary`

- Type: `string`; Required: yes
- Purpose: Secondary executor tag.

#### `threshold`

- Type: `integer`; Required: no; Default: `500`
- Unit: milliseconds
- Purpose: Standby delay; `0` allows immediate execution and takeover.
- Compatibility: Earlier versions treated explicit `0` as `500` ms. Set `500` explicitly to preserve that behavior.

#### `always_standby`

- Type: `boolean`; Required: no; Default: `false`
- Purpose: Keep the secondary in standby for all requests rather than only after the threshold condition.

#### `short_circuit`

- Type: `boolean`; Required: no; Default: `false`
- Purpose: Stop the executor chain after fallback selects the winning response.

### Behavior

- Provides controlled degradation instead of unconditional double-querying.
- Useful when one path is usually faster but another path is more complete or stable.
- With `short_circuit` enabled, the winning branch writes its response and then immediately stops the remaining executor chain.

### Metrics

Exported through the global `GET /api/metrics` endpoint:

- `fallback_primary_total`
- `fallback_primary_error_total`
- `fallback_secondary_total`

### Typical Uses

- Low-latency primary plus stable backup
- Tail-latency protection

<Admonition type="note" title="Notes">

- A too-aggressive threshold can turn the secondary into a routine dependency.

</Admonition>

## `load_balance`

<PluginAvailability from="minimal" />

### Purpose and configuration

Selects one executor subcall per invocation, including complete `sequence` branches.

```yaml
- tag: balance_main
  type: load_balance
  args:
    strategy: weighted_random
    executors:
      - exec: seq_dns_a
        weight: 3
      - exec: seq_dns_b
        weight: 1
```

| Field | Default | Description |
| --- | --- | --- |
| `strategy` | `round_robin` | `round_robin` follows configuration order; `random` selects uniformly; `weighted_random` selects in proportion to weights |
| `executors` | Required | Non-empty object array with distinct targets |
| `executors[].exec` | Required | Plain executor tag without `$`; quick-setup expressions are not supported |
| `executors[].weight` | `1` | Positive `u32` integer (`1..4294967295`), used only by weighted random |

Weights `3:1` yield probabilities `3/4:1/4`, without exact short-term counts.
Missing references, wrong plugin kinds, self-references, and dependency cycles are rejected at startup.

### Execution semantics

- Executes one target per call. Errors propagate unchanged; compose `fallback` for failover.
- Natural completion and `return` resume the caller. `Stop`, including `accept`, `reject`, and cache-hit short-circuiting, propagates outward.
- A normal return without a response remains normal completion. DNS RCODEs do not determine execution failure.
- The branch uses the current context directly, retaining request, response, marks, and extension state.
- The subcall receives no outer continuation. Put middleware such as `ecs_handler` and `cache` together with its downstream stages inside a target `sequence`.
- Round-robin starts at the first item and shares an atomic cursor per instance. Concurrent calls rotate in selection order, not completion order. Failed or cancelled calls consume their selection; reload resets the cursor.
- Ratios count invocations entering this plugin, including branch cache hits. Client caching does not participate, and these ratios do not represent link bandwidth.

### Distribute requests across two DNS resolution chains

For example, use two DNS resolver services for the same queries, with each resolution chain caching its own results.
This complete configuration alternates between `seq_dns_a` and `seq_dns_b`, then checks the selected branch's cache or queries its upstream.

```yaml
plugins:
  - tag: cache_dns_a
    type: cache
    args:
      size: 1024
      short_circuit: true
  - tag: cache_dns_b
    type: cache
    args:
      size: 1024
      short_circuit: true
  - tag: forward_dns_a
    type: forward
    args:
      upstreams:
        - addr: "udp://1.1.1.1:53"
  - tag: forward_dns_b
    type: forward
    args:
      upstreams:
        - addr: "udp://8.8.8.8:53"
  - tag: seq_dns_a
    type: sequence
    args:
      - exec: $cache_dns_a
      - exec: $forward_dns_a
  - tag: seq_dns_b
    type: sequence
    args:
      - exec: $cache_dns_b
      - exec: $forward_dns_b
  - tag: balance_main
    type: load_balance
    args:
      strategy: round_robin
      executors:
        - exec: seq_dns_a
        - exec: seq_dns_b
  - tag: udp_server
    type: udp_server
    args:
      listen: "127.0.0.1:5335"
      entry: balance_main
```

Branch cache hits still participate in round-robin selection. To send more requests to one chain, switch to `weighted_random` and assign weights such as `3:1`.
A shared cache that short-circuits before `load_balance` limits branch selection to cache misses.

### Metrics

Exported through global `GET /api/metrics`, with `plugin_tag` and `executor` labels:

- `load_balance_selected_total`: branch selections, including subsequently cancelled calls.
- `load_balance_error_total`: selected calls returning execution errors. Normal completion without a response is not an error.

There is no dedicated management API, quick setup, automatic retry, or health checking.
