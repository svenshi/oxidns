---
title: Configuration API
---

The configuration API only handles native OxiDNS YAML. Standard and Expert are WebUI workspace concepts; the backend does not accept intents, plans, or mode ownership.

## Read and validate

### `GET /api/config`

Returns the exact configuration file selected at startup, its path, SHA-256 `version`, and modification time. Expanded environment values are never written back.

### `GET /api/config/check`

Checks the current on-disk configuration at its real path, including environment variables, `include`, and relative paths.

### `POST /api/config/validate`

Validates candidate YAML without writing it. The recommended request is:

```json
{
  "format": "yaml",
  "content": "plugins:\n  - tag: forward\n    type: forward\n"
}
```

Raw UTF-8 YAML remains accepted for compatibility. The candidate is preflighted beside the real configuration file, so `include` and relative paths have the same semantics as Apply. A successful response includes the candidate `version`, plugin count, dependency graph, and initialization order.

## Atomic apply

### `POST /api/config/apply`

Starts a generic configuration transaction with optimistic concurrency control:

```json
{
  "format": "yaml",
  "content": "...",
  "base_version": "current disk version",
  "candidate_version": "candidate version returned by validate"
}
```

Rules:

- Content is limited to 2 MiB. The server recomputes the candidate version and performs full validation again.
- `base_version` must equal the current disk version. A forged candidate version, active transaction, or reload in progress returns `409 Conflict`.
- Accepted requests return `202 Accepted` with a `config-{timestamp}-{pid}-{hash12}` transaction ID, before/after versions, and `pending` status.
- The server uses atomic file replacement. If reload or runtime assembly fails, both the disk configuration and the previous healthy runtime are restored.

### `GET /api/config/apply/status`

Returns the active or latest transaction ID, state, before/after versions, and error. After `202`, clients should poll until `committed` or `rolled_back`.

## Healthy history

### `GET /api/config/history`

Lists versions that have run successfully without including YAML content in the list response. History retains at most 20 entries and 20 MiB of YAML, deduplicates identical versions, and evicts the oldest entries first.

### `POST /api/config/history/restore`

Send `{"id":"history-entry-id"}`. This endpoint returns only a YAML preview; it neither writes nor reloads configuration. Read the current configuration version, then submit the preview through `/config/validate` and `/config/apply` to activate it.

History is a non-critical add-on. A history write failure is logged but never rolls back a configuration that is already running successfully.

## Compatible save endpoint

### `PUT /api/config`

The request remains compatible:

```json
{
  "format": "yaml",
  "content": "...",
  "base_version": "sha256-hex",
  "validate": true,
  "reload": false
}
```

- `reload: false` atomically replaces the file under the shared configuration lock and does not change the running configuration.
- `reload: true` enters the same generic transaction used by `/config/apply`.
- Every configuration writer shares one lock, preventing Save, Apply, and reload from overwriting each other.

Transaction sidecars live beside the configuration file: `.config-transaction.json`, `.config-transaction.last.json`, and `.config-history.json`. If startup discovers a pending journal, OxiDNS restores the previous healthy YAML before loading configuration.
