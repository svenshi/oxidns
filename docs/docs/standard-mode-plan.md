# 标准模式产品定位与分阶段开发计划

## 1. 文档目的

本文定义 OxiDNS 标准模式的产品定位、范围边界、配置编译架构、当前实现基线、分阶段开发路径和阶段验收门槛。

本文是维护者用于拆分 Issue、Milestone 和 Pull Request 的规划基线，不是发布日期或兼容性承诺。具体排期仍以项目 Issue、Milestone 和实际 Release 为准；当标准模式的产品边界、核心编译语义或阶段目标发生变化时，应先更新本文，再开始扩展功能。

## 2. 产品定位

### 2.1 一句话定位

标准模式是一个跨平台、完全基于 OxiDNS 原生能力的 DNS 策略控制面与配置编译器。

它把用户能够理解的 DNS 意图，确定性地编译为 OxiDNS 的 server、executor、matcher 和 provider 插件图，并负责验证、预览、应用、解释和回滚。

```text
用户意图
  -> 规范化与迁移
  -> 语义校验
  -> 策略计划 PolicyPlan
  -> OxiDNS 插件图 PluginGraph
  -> 配置预检
  -> 原子应用
  -> 运行解释与回滚
```

### 2.2 目标用户

标准模式主要面向：

- 希望使用 OxiDNS，但不希望直接维护 YAML 和插件依赖图的用户；
- 需要缓存、过滤、分流、上游容错、ECS、双栈和查询解释等常见 DNS 策略的用户；
- 在 Linux、Windows、macOS、BSD、容器、NAS 或其他环境独立运行 OxiDNS 的用户；
- 希望从表单化策略起步，并在必要时切换到专家模式的用户。

标准模式不假设 OxiDNS 部署在路由器上，也不假设请求来自任何特定网关、代理或操作系统网络栈。

### 2.3 核心价值承诺

标准模式必须同时满足：

1. **不要求理解 YAML**：用户以业务意图配置策略，而不是手工拼装插件。
2. **行为可预测**：每个选项都有明确的运行时语义，不存在“保存成功但没有生效”的字段。
3. **配置可验证**：保存前完成引用、能力、冲突、DNS 语义和资源边界校验。
4. **应用可回滚**：配置、标准模式状态和运行时要么一起成功，要么继续使用上一版本。
5. **请求可解释**：能够说明一次查询命中了什么规则、走了什么路径、使用了哪个缓存和上游，以及为什么发生回退。
6. **能力不被削弱**：标准模式是对 OxiDNS 插件图的高层编译，而不是另建一套功能受限的 DNS 运行时。
7. **跨平台且自包含**：所有标准模式功能只依赖 OxiDNS 自身公开能力。

## 3. 产品边界

### 3.1 标准模式负责的内容

标准模式可以管理：

- OxiDNS 自身的 UDP、TCP、DoT、DoH、DoH3 和 DoQ 监听器；
- 上游服务器、上游组、连接参数、bootstrap、dial address 和 OxiDNS 原生 outbound；
- 并发选择、有序回退和主备容错；
- 正缓存、负缓存、lazy cache、持久化及缓存运维；
- 广告过滤、允许规则、阻断规则、规则订阅和 Provider 生命周期；
- hosts、redirect、本地合成响应、TTL 和 QTYPE 策略；
- 域名、客户端 IP/CIDR、QTYPE、响应 IP、CNAME、RCODE 等原生规则；
- 国内、国外、自定义和未知域名解析路径；
- ECS、IPv4/IPv6 优先、IPv4-only/IPv6-only 和响应 IP 优选；
- 基于 OxiDNS 原生 `dynamic_domain_set` 与 `learn_domain` 的动态域名学习；
- 查询日志、指标、执行轨迹、配置解释和诊断；
- 标准模式状态、配置历史、导入、导出、预览、应用和回滚；
- OxiDNS 自身的日志级别、工作线程、API 和运行参数。

### 3.2 明确不负责的内容

标准模式不执行、不配置、也不依赖：

- OpenWrt UCI 或 LuCI；
- dnsmasq、systemd-resolved、NetworkManager 或其他系统 DNS 服务；
- nftables、iptables、pf、防火墙规则或 53 端口劫持；
- DHCP、MAC 地址、租约或第三方设备发现；
- 操作系统 DNS 设置修改；
- Clash、sing-box、mihomo 或其他代理软件的专属 API、端口和配置模型；
- 第三方 FakeIP 地址池和代理模式；
- RouterOS、ipset、nftset 等网络副作用；
- 第三方服务的安装、启动、停止、恢复或配置同步。

这些能力可以继续作为专家模式插件、独立集成项目或外部控制器存在，但不得成为标准模式配置模型和运行流程的依赖。

### 3.3 “DNS 防泄漏”的产品语义

在上述边界下，标准模式中的“DNS 防泄漏”只能指 **OxiDNS 上游策略防泄漏**：

> OxiDNS 不会把某类域名或未知域名发送给策略不允许的上游组，并且不会在受保护路径失败时静默切换到被禁止的路径。

它不代表：

- 拦截未经过 OxiDNS 的客户端 DNS 请求；
- 阻止浏览器或应用使用自己的 DoH；
- 修改系统路由或防火墙；
- 自动控制第三方代理。

WebUI 文案、帮助和诊断必须清楚表达这个边界，避免把“严格远程解析”描述成整机或整网 DNS 防泄漏。

## 4. 与专家模式的关系

标准模式和专家模式共享同一个 OxiDNS 运行时，但拥有不同的配置入口：

- 标准模式维护结构化意图，并拥有由该意图生成的插件和文件；
- 专家模式允许直接编辑完整 YAML 和任意插件图；
- 标准模式可以提供“查看生成 YAML”和“复制为专家配置”；
- 专家配置不能在没有明确导入规则的情况下自动反向转换为标准模式意图；
- 从专家模式进入标准模式时，现有配置必须被标记为 `unmanaged`，禁止无预览直接覆盖；
- 标准模式生成后被专家模式修改时，状态必须变为 `modified`，后续应用前必须展示差异。

配置所有权至少包含三种状态：

| 状态 | 含义 | 标准模式行为 |
|---|---|---|
| `managed` | 当前配置由本标准意图生成，版本一致 | 允许正常计划和应用 |
| `modified` | 标准模式生成后配置被外部修改 | 必须展示 Diff 和覆盖范围 |
| `unmanaged` | 当前配置从未由标准模式接管 | 必须导入受支持部分、另存配置或确认替换 |

## 5. 参考项目的吸收原则

标准模式参考 [sbwml/luci-app-mosdns](https://github.com/sbwml/luci-app-mosdns) 和 [jasonxtt/mosdns](https://github.com/jasonxtt/mosdns) 的 DNS 策略编译经验，但不复制它们的平台绑定和固定配置结构。

### 5.1 应吸收的设计

#### 来自 sbwml/luci-app-mosdns

- 一个功能开关必须改变完整的执行链，而不是只保存状态；
- 国内域名、国外域名和未知域名使用明确的解析路径；
- 国内上游响应可以通过 IP Provider 校验，并在异常时触发远程回退；
- ECS、IPv4 优先、缓存、TTL、广告过滤、DDNS 和流媒体路径有明确插入位置；
- hosts、redirect、缓存、规则、分流和 fallback 的顺序是产品行为的一部分。

#### 来自 jasonxtt/mosdns

- 结构性变化与轻量策略切换分开处理；
- 不同解析语义使用不同缓存，避免路径和模式之间串用结果；
- 专属分流组应生成 Provider、缓存、上游、Sequence 和可选监听器的完整 Bundle；
- 白名单、黑名单、DDNS、专属分组、国内外规则和未知域名处理必须有稳定优先级；
- 查询日志应展示最终有效路径和上游，而不是只罗列中间插件；
- 未知域名可以根据响应 IP 结果学习到 OxiDNS 自身的动态域名集合。

### 5.2 不吸收的设计

- Shell/UCI 配置生成；
- 固定编号的 `switch1...switch17`；
- 固定 bit、mark、slot 或预留端口；
- 针对特定操作系统的文件路径和服务控制；
- 针对第三方代理的 FakeIP、端口和控制逻辑；
- 把部署系统操作混入 DNS 策略编译器。

OxiDNS 应吸收其策略语义，并使用命名清晰、类型化、可迁移的原生模型重新实现。

## 6. 当前实现基线

### 6.1 已形成的基础

当前标准模式已经具备：

- Schema v2 标准模式状态及旧版本迁移；
- DNS、过滤、路由、例外、设备、查询日志和总览页面；
- 上游地址和协议转换；
- 上游连通性测试；
- 基础 forward、path sequence、cache、filter 和 server 配置生成；
- 广告规则订阅下载、定时刷新和 Provider reload；
- 客户端 IP/CIDR 设备策略；
- 查询记录及标准标签到路径、规则和上游组的解释元数据；
- 构建能力感知；
- 标准状态的原子文件写入与版本冲突保护；
- 生成配置提交到现有配置校验和运行时 reload 流程。

因此当前实现不是页面原型，而是已经形成了端到端骨架。下一步重点应是修正编译语义和安全边界，而不是继续增加页面数量。

### 6.2 当前发布判断

当前标准模式应继续标记为 **Alpha / Experimental**，不应默认推荐给已有专家配置的用户。

主要原因是当前仍存在用户意图、生成配置和运行时行为不一致的问题。

### 6.3 P0 缺口

#### 配置接管和事务

- 专家模式切换标准模式缺少导入、Diff 和破坏性确认；
- 标准状态、DNS YAML、生成元数据和运行时分别提交，不构成一个事务；
- 缺少生成元数据时，现有配置可能被误判为未失步；
- 标准模式保存会重新生成完整插件列表，但只保留有限的顶层配置；
- 标准系统页面复用了专家设置，标准生成器后续可能覆盖其中部分值。

#### 编译语义

- cache 生成器使用 `min_ttl`、`max_ttl`、`negative_ttl`，与运行时实际字段不一致；
- 所有路径共用一个 `standard_cache`，而缓存键不包含路径或上游组；
- `parallel`、`fastest` 和 `sequential` 没有正确映射到 `response_selection` 或显式 fallback；
- 路径级过滤和查询日志开启不会始终触发对应插件生成；
- `dualStack`、`ipSelection`、`ecs` 和查询日志采样率存在于状态模型，但没有完整编译；
- `runtime.threads` 与 Rust 配置中的 `runtime.worker_threads` 不一致；
- 构建能力不足时存在静默跳过插件的可能，用户看不到完整降级结果。

#### 功能闭环

- 标准页面主要维护默认上游组，其他组缺少完整 CRUD；
- 路由可以引用路径和组，但用户难以完成“创建组 -> 创建路径 -> 创建规则 -> 测试”的闭环；
- 场景模板只创建部分路径草稿，没有生成与名称相符的完整策略；
- 订阅的单独更新周期最终被合并为最短周期；
- 标准模式核心 Schema、生成器、迁移、继承矩阵和解释器缺少直接自动化测试。

## 7. 目标配置编译架构

### 7.1 权威边界

Rust 后端应成为标准模式规范化、语义校验、能力规划、配置生成和提交的权威实现。

WebUI 负责：

- 收集和展示用户意图；
- 提供本地表单校验和即时反馈；
- 展示后端返回的计划、诊断、Diff 和解释；
- 不单独定义最终运行语义。

后端负责：

- Schema 迁移与规范化；
- 全局引用和冲突校验；
- 构建能力和运行能力检查；
- PolicyPlan 和 PluginGraph 生成；
- 配置分析、暂存、切换和 runtime reload；
- 生成元数据、版本和回滚历史。

前后端可以共享 JSON Schema 或生成类型，但不能长期维护两套独立的编译规则。

### 7.2 核心对象

```text
StandardIntent
  listeners
  upstreamGroups
  resolutionPaths
  filteringPolicy
  routingPolicy
  exceptionPolicy
  clientPolicies
  cacheDefaults
  observability
  runtime

PolicyPlan
  normalizedIntent
  providers
  upstreamRoles
  pathBundles
  orderedRules
  requiredCapabilities
  managedFiles
  diagnostics
  ownership

PluginGraph
  plugins
  dependencies
  entrypoints
  tagMap
  config
```

`StandardIntent` 是用户配置，`PolicyPlan` 是可解释的策略计划，`PluginGraph` 是运行时配置产物。WebUI 不应直接要求用户理解 `PluginGraph`，但必须允许高级用户查看它。

### 7.3 特性编译器

编译过程应拆分为可独立测试的特性编译器：

```text
compileRuntime()
compileListeners()
compileRuleSources()
compileFilteringPolicy()
compileUpstreamGroups()
compileCachePolicy()
compileResolutionPaths()
compileDualStackPolicy()
compileEcsPolicy()
compileIpSelectionPolicy()
compileRoutingPolicy()
compileClientPolicies()
compileObservability()
```

每个编译器至少返回：

- 生成的插件和依赖；
- 用户意图到生成标签的映射；
- 所需构建能力；
- 管理的文件和运行资源；
- 错误、警告和可选建议；
- 对请求热路径的影响摘要。

### 7.4 编译器不变量

标准模式编译器必须满足：

1. 相同规范化意图和相同能力集产生相同配置；
2. 所有引用在生成前解析，禁止静默 fallback 到第一个组或路径；
3. 用户请求的核心能力缺失时编译失败，而不是跳过；
4. 只有明确标记为可选的观测能力允许降级，并必须显示警告；
5. 每个具有不同解析语义的 Path 使用独立缓存实例；
6. ECS 路径必须明确决定 ECS 是否参与缓存键；
7. 任何显示在 UI 中的设置都必须有生成测试证明其改变执行图；
8. 所有自动标签稳定、唯一，并可从运行轨迹映射回用户对象；
9. 标准模式只管理自身声明拥有的配置节点和文件；
10. 编译和应用不在 DNS 请求热路径执行。

## 8. 标准模式核心策略语义

### 8.1 Resolution Path Bundle

解析路径不是一个上游引用，而是一个完整策略 Bundle。目标结构为：

```text
Path
  query recorder
  filtering policy
  dual-stack policy
  ECS policy
  IP selection policy
  path-scoped cache
  forward or fallback
  response TTL policy
  accept
```

不同路径不能共享会改变结果语义的状态，包括缓存、ECS 缓存键、动态学习集合和探测评分。只有明确证明结果等价的资源才能共享。

### 8.2 上游策略

标准模式应使用与运行时一致的名称：

| 用户策略 | 编译结果 |
|---|---|
| `fastest` | `forward.response_selection: fastest` |
| `balanced` | `forward.response_selection: balanced` |
| `prefer_positive` | `forward.response_selection: prefer_positive` |
| `consensus` | `forward.response_selection: consensus` |
| `ordered_fallback` | 一个或多个显式 `fallback` 组成的有序主备链 |

`concurrent: 1` 不等价于有序回退，不能继续使用 `sequential` 名称表达该行为。

### 8.3 上游防泄漏模式

阶段二引入三种未知域名策略：

| 模式 | 未知域名编译语义 |
|---|---|
| 兼容优先 | 国内路径先查询并校验响应 IP，失败或超时后远程回退 |
| 隐私优先 | 远程路径优先，仅在没有有效结果时允许国内回退 |
| 严格远程 | 只允许远程路径；失败时返回失败，不允许国内或默认路径回退 |

严格远程模式必须验证：

- 远程组存在且至少有一个启用上游；
- 路径中不存在国内组引用；
- fallback 中不存在被禁止的分支；
- 域名形式的加密上游有明确 bootstrap 或 dial address；
- 使用显式 outbound 时不允许静默回退默认 outbound；
- 配置计划明确说明失败时的 RCODE 和 fail-open/fail-closed 语义。

### 8.4 规则优先级

标准模式维护稳定的系统优先级：

| 顺序 | 规则类别 | 说明 |
|---:|---|---|
| 1 | 本地 hosts / redirect | 优先生成本地或重写后的结果 |
| 2 | 强制阻断 | 用户明确配置的硬阻断 |
| 3 | 允许 / 跳过过滤 | 对广告和订阅过滤的例外 |
| 4 | DDNS | 默认绕过普通缓存，可配置短 TTL 和专用路径 |
| 5 | 客户端 IP/CIDR 策略 | 只使用 OxiDNS 实际看到的源地址 |
| 6 | 专属解析路径 | 用户配置的高优先级专属组 |
| 7 | 用户强制路由规则 | 按显式顺序匹配 |
| 8 | 国内域名 | 国内路径 |
| 9 | 国外域名 | 远程路径 |
| 10 | 未知域名 | 按上游防泄漏模式处理 |
| 11 | 响应校验和回退 | `resp_ip`、`rcode`、`has_wanted_ans` 等 |
| 12 | 响应后处理和记录 | TTL、IP 优选、解释和最终收口 |

同一类别内允许用户排序；跨类别调整仅在专家模式开放。编译计划必须展示最终有效顺序。

## 9. 分阶段开发计划

阶段使用完成门槛而不是日期定义。不得为了发布版本号跳过前一阶段的安全和语义要求。

### 阶段 0：编译器可信化

#### 目标

消除现有标准模式中的静默失效、缓存串线、模式接管和非原子应用风险，使标准模式从 Alpha 进入 Beta。

#### 工作包

##### SM-0.1 修复确定性编译错误

- 将缓存字段改为运行时实际支持的 `min_positive_ttl`、`max_positive_ttl`、`max_negative_ttl` 和 `negative_ttl_without_soa`；
- 为每个启用缓存的 Resolution Path 生成独立缓存；
- 为使用 ECS 的路径设置正确的 `ecs_in_key`；
- 正确生成 `runtime.worker_threads`；
- 修复路径级过滤和查询日志对插件生成条件的影响；
- 禁止无效路径引用静默回退第一个上游组；
- 将上游策略映射到真实 `response_selection` 或 `fallback`；
- 暂时隐藏尚未编译的 ECS、双栈、IP 优选、采样率和场景选项。

##### SM-0.2 统一语义校验

- 建立单一的 `validateStandardIntent`；
- 检查 ID、名称、自动标签和文件名唯一性；
- 检查组、路径、规则、设备和 Provider 引用；
- 检查循环依赖、空上游组和无入口插件；
- 检查监听器冲突和端口格式；
- 区分错误、警告和建议；
- 核心能力缺失时阻止应用，移除静默 `skippedCapabilities`。

##### SM-0.3 配置所有权和安全切换

- 实现 `managed / modified / unmanaged`；
- 专家配置进入标准模式时提供只读分析、支持项导入或确认替换；
- 显示将被保留、接管和删除的配置；
- 标准模式只修改声明拥有的顶层字段和插件；
- 修复标准系统设置与专家设置的双写问题。

##### SM-0.4 Plan/Apply 事务

- 增加后端 `standard/plan`；
- 增加后端 `standard/apply`；
- 同时校验标准状态版本和 DNS 配置版本；
- 在暂存区完成生成配置分析和 replacement runtime 初始化；
- replacement runtime 成功后再提交标准状态和生成元数据；
- 任一步失败时继续使用上一运行时和上一管理状态；
- 记录最近成功版本和失败诊断。

##### SM-0.5 编译器测试基线

- 默认意图 golden config；
- 每个字段的输出差异测试；
- 全局、路径、客户端三级继承矩阵；
- 每路径缓存隔离；
- ECS cache key；
- 上游选择和 fallback 语义；
- 缺失能力矩阵；
- Schema 迁移和损坏状态恢复；
- 专家到标准模式切换；
- 版本冲突和失败回滚；
- live UDP/TCP 请求验证最终路径。

#### 阶段门槛

- UI 中不存在没有运行时效果的设置；
- 标准模式直接测试覆盖所有编译模块；
- 相同输入生成稳定配置和稳定标签；
- 不同路径不会共享 DNS 结果缓存；
- Apply 失败不会改变当前运行时或标准状态；
- 未管理配置不会被无确认覆盖；
- WebUI typecheck、lint、test、build 和 Rust 完整质量门禁通过。

### 阶段 1：OxiDNS Native Standard 1.0

#### 目标

交付一个跨平台、稳定、自包含的基础 DNS 产品。用户可以完成常见解析、过滤、缓存和路由任务，不需要理解插件图。

#### 工作包

##### SM-1.1 完整上游组管理

- 新增、编辑、删除和复制上游组；
- 管理组内上游及启用状态；
- 支持 OxiDNS 已编译的上游协议；
- 支持 bootstrap、dial address、TLS 校验、超时、pipeline 和 HTTP/3；
- 支持通用 OxiDNS outbound 和 SOCKS 字段，但不连接或控制任何第三方软件；
- 提供单上游和整组测试；
- 显示构建能力、协议可用性和失败原因。

##### SM-1.2 Resolution Path Bundle

- 路径完整 CRUD；
- 绑定上游组；
- 独立过滤、缓存和日志继承；
- 编译稳定的路径标签和解释元数据；
- 在同一页面完成“上游组 -> 路径 -> 规则”的关联导航；
- 删除路径前展示所有引用。

##### SM-1.3 基础过滤闭环

- 手工允许和阻断规则；
- 本地文件和在线订阅；
- 明确允许规则优先级；
- 每个订阅独立更新，或在产品模型中改为一个全局周期；
- 下载失败保留最后成功文件；
- 只有新文件校验成功后才 reload Provider；
- 支持 NXDOMAIN、NODATA、NULL 和 REFUSED；
- 展示订阅最近成功、最近错误、规则数量和手动刷新。

##### SM-1.4 原生本地策略

- hosts；
- redirect；
- 本地合成响应；
- TTL 范围；
- HTTPS/SVCB、AAAA 等 QTYPE 策略；
- DDNS 规则，默认绕过普通缓存并支持短 TTL；
- 所有功能只编译为 OxiDNS 原生插件。

##### SM-1.5 运行与诊断

- 查询历史查看、清理和导出；
- 缓存查看、清理、dump 和 load；
- 上游运行统计；
- 路径和规则命中解释；
- Provider、download、cron 和 reload 状态；
- 配置历史和一键回滚。

#### 阶段门槛

用户能够稳定完成：

```text
创建上游组
  -> 创建解析路径
  -> 开启独立缓存和过滤
  -> 添加路由规则
  -> 预览生成计划
  -> 应用
  -> 用查询日志确认最终路径
  -> 回滚
```

默认方案只承诺安全、通用的 DNS 解析、缓存和过滤，不在本阶段宣称智能国内外分流。

### 阶段 2：原生智能分流与上游防泄漏

#### 目标

使用 OxiDNS 原生 matcher、provider、sequence、forward、fallback 和 cache，实现可解释的国内、国外和未知域名分流。

#### 工作包

##### SM-2.1 语义化规则数据

- 引入 `domestic_domains`、`foreign_domains`、`domestic_ips`、`direct_domains`、`remote_domains` 和 `ddns_domains` 等角色；
- 角色可以绑定内置数据、本地文件、在线订阅或手工规则；
- 编译器不依赖固定文件名或固定订阅地址；
- 数据不存在、过期或下载失败时给出明确诊断。

##### SM-2.2 国内和远程路径

- 国内路径使用独立上游、缓存和可选双栈策略；
- 远程路径使用独立上游、缓存、ECS 和 outbound；
- 国内响应通过 `resp_ip` 和国内 IP Provider 校验；
- 不符合策略的响应通过 `drop_resp` 触发显式 fallback；
- NODATA、NXDOMAIN、SERVFAIL、CNAME-only 和超时分别定义回退行为。

##### SM-2.3 未知域名模式

- 兼容优先；
- 隐私优先；
- 严格远程；
- 每个模式使用独立缓存或稳定独立 namespace；
- 模式变化时不复用语义不兼容的缓存；
- 查询解释显示初始路径、校验结果、回退原因和最终上游。

##### SM-2.4 ECS、双栈和 IP 优选

- ECS 支持移除、保留客户端 ECS、按客户端生成和固定 preset；
- 使用 ECS 的缓存明确设置 `ecs_in_key`；
- `prefer_ipv4` 和 `prefer_ipv6` 在 forward 前按 continuation 语义编译；
- IPv4-only/IPv6-only 使用 QTYPE 策略，不与偏好策略混淆；
- `ip_selector` 独立于上游响应竞速和双栈抑制；
- DNSSEC 场景遵循 `reorder_only` 或 `skip` 安全策略。

##### SM-2.5 固定优先级与冲突解释

- 实现本文第 8.4 节的系统优先级；
- 同类规则支持排序；
- 跨类别冲突由编译器诊断；
- 计划中展示被覆盖、不可达和重复规则；
- 查询解释显示最终生效规则，而不是仅显示第一个中间匹配器。

#### 阶段门槛

- 严格远程模式下未知域名不会执行国内或默认上游；
- 国内响应 IP 校验失败能稳定进入配置的远程回退；
- 模式、路径、ECS 和客户端策略之间不存在缓存串线；
- 所有 fallback 情况都有确定测试：成功、无响应、负响应、超时和传输失败；
- 一次查询能够解释“为什么命中、为什么回退、最终使用什么”；
- 文案明确上游防泄漏的能力边界。

### 阶段 3：原生高级 DNS 策略

#### 目标

在不引入第三方系统耦合的前提下，扩展 OxiDNS 原生策略能力和场景表达。

#### 工作包

##### SM-3.1 专属解析组

每个专属组编译为：

```text
规则 Provider
  + 手工规则
  + 上游组
  + 独立缓存
  + ECS / 双栈 / IP 优选
  + Resolution Path
  + 可选 OxiDNS 原生监听器
```

支持工作网络、流媒体、教育网络、隐私 DNS、内部域名和区域上游等通用场景，不包含第三方代理专属语义。

##### SM-3.2 原生动态学习

- 使用 `dynamic_domain_set` 保存动态结果；
- 使用 `learn_domain` 在响应分类后学习域名；
- 使用 `resp_ip`、`rcode` 和 `has_wanted_ans` 决定学习条件；
- 限制集合容量、批量写入和并发队列；
- 提供清理、暂停、手工纠错和查看入口；
- 在支持老化语义前不得默认永久信任自动学习结果；
- 动态集合始终低于手工 allow/block 和强制路由的优先级。

##### SM-3.3 高级规则

- 时间规则；
- CNAME 和 RCODE 路由；
- rate limiter；
- 多上游一致性；
- 按 QTYPE 使用不同路径；
- 失败开放/失败关闭策略；
- 高级规则仍使用统一 PolicyPlan 和解释模型。

##### SM-3.4 真实场景模板

场景模板必须生成完整策略，不允许只创建名称或路径草稿。例如一个“低延迟解析”模板至少需要生成：

```text
目标域名 Provider
  + 低延迟上游组
  + IP Selector
  + 独立缓存
  + Resolution Path
  + 路由规则
  + 解释标签
```

模板应用前必须展示将新增和修改的对象，不能覆盖用户已有同名资源。

#### 阶段门槛

- 所有模板都有 golden config 和真实查询测试；
- 动态学习失败不影响 DNS 主链路，除非用户显式选择 fail-closed；
- 动态规则具有容量、清理和纠错机制；
- 专属路径资源可以完整创建、引用和删除，不遗留缓存或管理文件；
- 标准模式仍不依赖任何第三方服务。

### 阶段 4：解释、诊断与配置资产

#### 目标

让标准模式从“可以生成配置”提升为“可以长期运营和理解策略”的原生控制面。

#### 工作包

##### SM-4.1 编译解释

- 展示意图到 Provider、Matcher、Path、Cache 和 Upstream 的映射；
- 展示规则最终优先级；
- 展示每条路径的缓存边界和 ECS 行为；
- 展示所有自动生成标签；
- 展示当前构建缺少的可选能力；
- 提供只读 YAML 和插件依赖图。

##### SM-4.2 查询诊断

- 为什么未命中某条规则；
- 为什么选择默认路径；
- 为什么触发 fallback；
- 为什么缓存没有命中；
- 为什么 ECS 产生不同缓存项；
- 为什么响应 IP 校验失败；
- 为什么某个上游被排除或超时；
- 最终 RCODE、响应来源和耗时构成。

##### SM-4.3 配置资产

- 标准意图导入和导出；
- Schema 版本迁移；
- 配置版本历史；
- 语义 Diff，而不只是 YAML 文本 Diff；
- 从标准模式复制为专家配置；
- 对专家配置进行只读能力分析；
- 模板保存和复制，但不接入第三方模板服务。

#### 阶段门槛

- 用户可以从一次异常查询追溯到对应标准意图；
- 用户可以判断配置变化会影响哪些路径和规则；
- 导入、导出和迁移保留语义与稳定 ID；
- 任何标准模式版本都可以回滚到最近成功配置；
- 诊断功能不会向 DNS 请求热路径引入无界日志或高基数指标。

## 12. 发布与功能暴露规则

### Alpha

- 允许存在尚未稳定的 Schema；
- 必须显式标记 Experimental；
- 不允许静默覆盖专家配置；
- 未实现字段不得显示为可用。

### Beta

- 阶段 0 全部完成；
- 标准模式配置可以安全计划、应用和回滚；
- Schema 变更必须有迁移；
- 每个公开设置有编译测试。

### Standard 1.0

- 阶段 1 全部完成；
- 基础上游、路径、缓存、过滤和规则闭环稳定；
- 文档明确跨平台和不耦合第三方的边界；
- 默认方案可直接生成可运行配置。

### 后续版本

- 智能分流、上游防泄漏和动态学习分别按阶段门槛开放；
- 不使用版本号替代功能成熟度；
- 实验性原生插件必须在 UI 中继承其实验状态。

## 13. 产品和工程指标

标准模式不以页面数量和设置数量衡量完成度。应关注：

### 产品指标

- 默认方案首次应用成功率；
- 从创建上游到完成可用查询的步骤数；
- 配置失败时用户能否从诊断中定位原因；
- 查询记录能够映射到标准规则和路径的比例；
- 需要进入专家模式才能完成的基础场景比例。

### 正确性指标

- 显示但未编译的字段数量必须为零；
- 标准配置静默降级数量必须为零；
- 跨路径缓存误命中数量必须为零；
- Apply 失败导致状态分裂的数量必须为零；
- 严格远程模式访问禁止上游的数量必须为零。

### 性能指标

- 标准模式生成的主请求路径不得引入请求时规则解析；
- Provider、Matcher 和标签应在启动阶段完成规范化和绑定；
- 查询解释事件必须有界；
- 自动学习、下载和持久化不得在请求热路径执行阻塞 I/O；
- 新增路径和观测插件需要评估分配、锁和指标基数。

## 14. 实施原则

1. 先修语义和安全，再增加功能。
2. 每个产品选项必须对应一段可测试的编译规则。
3. 页面不能成为配置语义的唯一实现位置。
4. 不为兼容参考项目引入固定 tag、mark、slot 或文件名。
5. 不把第三方系统控制包装成标准模式功能。
6. 不把“能生成 YAML”视为完成，必须验证真实 DNS 行为。
7. 不用静默 fallback 掩盖无效引用和能力缺失。
8. 不让不同解析语义共享缓存和可变状态。
9. 保持 `server -> DnsContext -> matcher/executor/provider -> upstream -> response` 主路径。
10. 每个阶段只有通过退出门槛后才能作为下一阶段的依赖。

## 15. 最终验收定义

标准模式达到长期目标时，一名不了解 OxiDNS 插件体系的用户应当能够：

1. 创建和测试上游组；
2. 选择或创建解析路径；
3. 配置缓存、过滤、双栈、ECS 和回退意图；
4. 添加域名、QTYPE、响应和客户端规则；
5. 在应用前查看准确的策略计划和冲突；
6. 安全应用且不影响上一可用运行时；
7. 从查询日志理解最终路径、上游、缓存和回退原因；
8. 修改、导出、迁移或回滚标准意图；
9. 在需要任意插件编排时明确切换到专家模式；
10. 在整个过程中不依赖 OpenWrt、第三方代理或其他外部控制系统。

达到这一状态后，标准模式才真正成为 OxiDNS 原生能力的产品化入口，而不是专家 YAML 的简化编辑器。
